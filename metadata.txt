changelog=3.2.1
     3.2.1 2026-10
       **Fixed QGIS Hang on Plugin Load (Windows/macOS)**
       * Removed the startup dependency check that shelled out to "sys.executable -m pip install --upgrade -r requirements.txt" whenever scipy was below 1.17.0. On QGIS's bundled Python, sys.executable is the QGIS executable itself (not python.exe), so that command launched a second QGIS instance instead of running pip; the first QGIS then hung on the main thread waiting for it to close, with no timeout, and the command's exit code was never checked, so the "dependencies updated" message shown afterwards was misleading in every case (pip never ran).
       * Lowered the scipy requirement from ">=1.17.0,<1.18" to ">=1.10", so the plugin's own check no longer fails against the scipy version QGIS itself bundles (e.g. 1.13.0 on QGIS 3.42). The plugin only ever used scipy.spatial.distance.euclidean (in the DBSCAN-based Create Virtual Stops tool); the tighter pin reflected alignment with the Stereoplot/Geochemistry Plotting Tools plugins' own numpy pin, not an actual GEOL-QMAPS requirement, and those two plugins don't depend on scipy at all.
       * Removed an unused "from scipy.spatial.distance import cdist" top-level import (cdist was imported but never called), so scipy is no longer imported at plugin load at all; it is now only imported lazily inside the Create Virtual Stops tool, where it was already being used.
       * Set plugin_dependencies=qpip in metadata.txt so the QGIS Plugin Manager can offer to install qpip automatically when installing GEOL-QMAPS, instead of relying solely on the manual step described in the README.
       * Fixed the Rejig tool failing with "Could not locate a QGIS_TEMPLATE folder" when updating a second project in a parent folder that already contains the latest template (left over from updating a first project there): the extracted template folder was located by diffing the parent folder's contents before/after extraction, so an already-present copy was wrongly treated as "nothing new"; it is now located directly from the downloaded archive's own top-level folder name, which works whether or not that folder already existed.
       * Fixed the Edit Dictionaries / Set User by Default tools leaving newly added (or deleted) dictionary items invisible to other layers' ValueRelation dropdowns: reload_csv() used to just call dataProvider().reloadData() on the one layer object passed in, which does not reliably pick up a table that a separate fiona/GDAL connection just dropped and recreated on disk (e.g. a brand new default User showed unresolved in curly braces on new features, because the "General // List of Users" layer that other layers' ValueRelation widgets query was still showing its pre-edit content even though the CSV/table itself, and the Edit Dictionaries delete dropdown which reads it fresh each time, already had the new entry). reload_csv() now forces a genuinely fresh read and refreshes every loaded layer sharing that name in place (not just the first match), since ValueRelation widgets are bound to layers by id, and a project can end up with more than one layer sharing a name after a merge or rejig.
       * Fixed the Synchronise QField to QGIS tool rejecting a QField package whose project file QFieldSync had written as .qgz instead of .qgs (it could produce either depending on its own settings/version): the package root used to be located by finding a .qgs file (never actually opened/read, just used to locate CURRENT_MISSION.gpkg relative to it), so a .qgz-based package falsely failed with "No .qgs project file found". The package root is now located directly from CURRENT_MISSION.gpkg itself, removing the dependency on the project file's format entirely.
       * Fixed the Export Compilation Layers to Common Themes tool always exporting data from whichever GEOL-QMAPS project was active the last time the plugin dock was (re)opened - typically the first one in the QGIS session - rather than the project currently active, if the user had since switched to a different one without reopening the plugin. The export's COMPILATION.gpkg path is now resolved fresh from the currently active project each time the tool runs.
       * Removed a redundant step in the same tool that re-wrote the "Layer" attribute on every feature of every CURRENT_MISSION layer before exporting: that field is already native to the GEOL-QMAPS schema and already populated when each feature is created, and in any case this step touched the CURRENT_MISSION layers, not the Compilation_ layers actually merged into the export, so it had no effect on the exported output - only an unnecessary edit/commit to the user's live field data on every export.
       * Thanks to the user who reported this with a detailed py-spy stack trace and root-cause analysis.
       **GEOL-QMAPS Template v3.2.1 Compatibility**
       * Renamed the Photographs_PT / Compilation_Photographs_PT "Azimut" field references to "Azimuth" throughout the plugin (image-direction map tip, the EXIF-to-Azimuth tool, and the in-memory photo layer built by the FieldMove import), matching the field rename made in GEOL-QMAPS template v3.2.1
       * Made the photo-layer map tip detect the Azimuth field dynamically instead of assuming it exists, since the same map tip is also applied to Sampling_PT/Compilation_Sampling_PT layers, which have no Azimuth field
       * Replaced the hard-coded Zenodo template download URL/version and extracted-folder name in the Rejig tool with dynamic resolution via GEOL-QMAPS' stable Zenodo "concept" record, so the tool automatically follows whichever template release is currently latest (past and future) without requiring a plugin code change at every template release
       **Import Tool Fix**
       * Fixed Step 3 (Generate QGIS Layers) of the Import Legacy Field Data tool silently generating no scratch layers at all: UUID hashing relied on the "Existing databases - raw data" column being encountered before "UUID" while looping over fields in schema order, but the template's actual field order has UUID first on every layer, so the hash was referenced before assignment (NameError) on every single row, silently dropping it. The hash and parsed value are now computed once per row from their column directly, independent of field order.
       **Copyright Notice**
       * Updated the copyright notice shown across the plugin windows to "2026 Centre for Exploration Targeting, School of Earth and Oceans, University of Western Australia. All Rights Reserved."
       **Cross-Version Field-Rename Awareness (Rejig & Merge Projects)**
       * Fixed the Rejig tool silently dropping a field's data when migrating an older project to the latest template if that field had since been renamed (e.g. Azimut/Reliabilit/Metamorphi/Deformatio/Stratigrap/Struct_Tec/Struc_Tect/Texture/DipDir/Width_mm): feature copying now falls back to the field's known historical name(s) whenever the current name doesn't exist on the source feature, so the value still carries over
       * Fixed the Merge Projects tool copying feature attributes by column *position* rather than by name, which could silently misassign values into the wrong field whenever the two projects' GeoPackages came from different template versions with different column layouts; attributes are now matched by name (with the same rename-aware fallback as Rejig)
       * Introduced a single shared, documented table of known historical field renames (FIELD_RENAME_RULES) used by both tools, making it straightforward to add future renames in one place
       * Reviewed the full template field/layer schema against the plugin's hard-coded field-name references; confirmed all other v3.2.1 field renames (Reliabilit->Confidence_Index/Reliability, Metamorphi->Index_Minerals, Deformatio->Strain_Intensity, Stratigrap->Stratigraphic_Unit, Struct_Tec/Struc_Tect/Texture->Strain_Pattern, DipDir->Dip_Dir, Width_mm->Width_m on Dikes-Sills_PT) require no further plugin code changes beyond the above
